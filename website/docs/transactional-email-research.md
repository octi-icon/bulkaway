# Branded pickup request email research

Research date: September 12, 2026. Sources are official product documentation, accessibility standards, and first-party email-platform guidance. Scope: the user confirmed both a branded team notification and a separate customer acknowledgment. Recommendations are design and implementation judgments, not claims of universal inbox compatibility or improved conversion.

## Existing contract

At inspection, [pickup.ts](../lib/pickup.ts) builds both HTML and plain text, but HTML is largely an escaped text dump inside a dark panel. [mail.ts](../lib/mail.ts) sends one message from `Bulk Away <mailer@wsitrashvalet.com>` to `service@bulkaway.com`, with the validated customer address as Reply-To. It uses implicit TLS, disables filesystem and URL reads by Nodemailer, and requires the service recipient to be accepted with no rejected recipients. [photos.ts](../lib/photos.ts) attaches normalized JPEG buffers with generated filenames.

[README.md](../README.md) at inspection says there is no automatic customer copy and no confirmed appointment until the scheduling system actually confirms one. The user has now authorized adding the customer acknowledgment, so update that documentation when implementation changes. [The pickup API](../app/api/pickup/route.ts) returns a reference after the delivery adapter succeeds; it does not reserve an appointment. Preserve the request-versus-booking boundary.

## Recommended message

Use the site's cream, plum, mustard and lime palette in a restrained operational layout: compact brand header, “New pickup request” heading, reference, prominent request status, contact details, location/date, item list, additional details, photo count, applicable offer, and consent record. Prefer readable text and sections to one large `<pre>` block. Exact colors, dimensions and hierarchy are project design choices.

Keep the preferred date explicitly labeled “Preferred date,” with a flexible fallback. State that pricing and pickup time need confirmation. Retain the existing quote-request caveat, SMS opted-in/declined state, exact disclosure/version/source/timestamp when opted in, and the statement that recording SMS preference does not activate texting. These are project requirements established in [pickup.ts](../lib/pickup.ts) and [README.md](../README.md), rather than claims derived from email standards.

Address a separate acknowledgment to the customer, say the request was received, show their reference and submitted summary, and explain that the crew will follow up to discuss the quote and timing. Set its Reply-To to the service mailbox. Do not promise a response deadline, approval, guaranteed discount eligibility, or booked date unsupported by the actual operation. Keep internal consent-processing instructions and uploaded-photo attachments in the team message; the customer can see a simple photo count and their SMS preference where useful. This is a recommendation based on the current request-versus-booking contract.

## Two-message delivery and partial success

Send the service notification first and verify its acceptance before attempting the acknowledgment. If service delivery fails or is uncertain, retain the existing request failure handling and do not tell the customer the request was received. If service delivery succeeds but the acknowledgment fails, retain the successful request reference and record the acknowledgment as unavailable; do not turn the whole request into a failure or resend the service message. Use wording such as “Your request was received. We couldn't confirm your email copy. Save this reference.” These are application decisions to prevent duplicate operational requests.

SMTP success transfers delivery responsibility to the accepting server; it is not proof of inbox placement. A timeout can occur after a server accepted the message, so retrying can create duplicates. This is why an acknowledgment timeout must not erase known service-message success. [RFC 5321, sections 4.2.5, 4.5.3.2.7 and 6.1](https://www.rfc-editor.org/rfc/rfc5321.html)

Keep independent Message-IDs for team and customer messages with the same human request reference. Cache the combined outcome under the existing idempotency key so repeated form submissions do not resend either message within that cache lifetime. The current process-local cache cannot guarantee deduplication across restarts or multiple server instances; avoid claiming durable exactly-once delivery. If stronger retry guarantees become necessary, use persistent per-message delivery state and a durable queue. These recommendations follow inspection of [the pickup API](../app/api/pickup/route.ts), not a claim that SMTP provides transactional rollback.

## Rendering and accessibility

- Use a fluid single-column outer table and an approximately 600px content area, with essential styles inline and common system fonts. Structural tables are a conservative approach for mixed email clients; Campaign Monitor's first-party implementation guide documents the continuing Outlook desktop constraint. Treat rounded corners and media queries as enhancements, with understandable content if ignored. [Campaign Monitor: Coding HTML emails](https://www.campaignmonitor.com/dev-resources/guides/coding-html-emails/)
- Gmail supports a documented CSS subset and media queries; unsupported rules can be ignored. Do not assume the website's external stylesheets, custom font loading, grid, animations or JavaScript transfer to email. Use explicit text/background colors, ordinary cell padding, wrapping long content, and simple links. [Google: Gmail CSS support](https://developers.google.com/workspace/gmail/design/css)
- Set `role="presentation"` on tables used only for layout, without data-table headers or captions. Preserve real headings and a logical reading order. W3C discourages layout tables on the web but gives this mitigation when existing layout tables are used; email compatibility is the reason for the exception here. [W3C WAI: Table tips](https://www.w3.org/WAI/tutorials/tables/tips/)
- Use descriptive link text, sufficiently large body text, and at least 4.5:1 contrast for ordinary text; 3:1 applies only to qualifying large text. Do not rely on accent color alone to convey state. [W3C: Contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)
- Give a meaningful logo a concise text alternative such as “Bulk Away”; use empty alt text when an image merely repeats adjacent text or is decorative. Essential request information must remain actual text. [W3C WAI: Alt decision tree](https://www.w3.org/WAI/tutorials/images/decision-tree/)

## Nodemailer and content safety

Keep complete `text` and `html` alternatives containing the same operational facts. Nodemailer supports both body fields and separate attachments; Reply-To is the appropriate routing field for customer replies while retaining the authenticated sender. Preserve transport-level `disableFileAccess: true` and `disableUrlAccess: true`, which prevent untrusted message data from causing arbitrary file reads or URL fetches. [Nodemailer: Message configuration](https://nodemailer.com/message)

A live-text Bulk Away wordmark with the existing palette is a simple default that avoids image dependencies. For an optional image logo, use a trusted PNG buffer as attachment `content`, give it a unique Content-ID, and reference the identical value with `src="cid:..."`. Nodemailer supports this embedded-image mechanism. Do not pass an attachment `path` or `href` that conflicts with existing protections. Keep the logo separate from the customer photo count, and preserve photo attachments when combining arrays. Logo visibility still needs client testing and alt-text fallback. [Nodemailer: Embedded images](https://nodemailer.com/message/embedded-images), [Nodemailer: Attachments](https://nodemailer.com/message/attachments)

Escape every customer-controlled value for its HTML context before insertion, including name, location, details, item formatting and reference. Encoding HTML text does not make arbitrary URLs, CSS or event handlers safe. Prefer plain text for customer fields; if adding `mailto:` or `tel:` links, construct them from validated values and encode the attribute independently. Do not embed raw user HTML, style rules, remote image URLs or manually composed message headers. [OWASP: Cross-site scripting prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

## Sender identity and delivery

Retain the existing authenticated sender address unless a new identity has actually been configured. Changing a display name is different from establishing a sending domain. Gmail requires SPF or DKIM for all senders to personal Gmail accounts and SPF, DKIM and DMARC for bulk senders; Google recommends all three generally. Domain alignment concerns the actual From domain, not the website branding or Reply-To address. Verify `wsitrashvalet.com` authentication in a real received message before claiming deliverability. This research does not verify DNS, provider configuration or inbox arrival. [Google: Email sender guidelines](https://support.google.com/mail/answer/81126?hl=en-GB)

Keep port 465 and implicit TLS together, the configured timeouts, certificate validation, and disabled raw-content logging. Nodemailer's SMTP documentation distinguishes port 465 implicit TLS from STARTTLS on port 587; a template redesign does not require a transport migration. [Nodemailer: SMTP transport](https://nodemailer.com/smtp)

## Verification before delivery claims

Test that both alternatives retain required fields, fallback values, offer and SMS variants; hostile HTML renders as text; each message has the correct sender/recipient and Reply-To; and attached-photo count excludes any brand image. Test service failure preventing acknowledgment, acknowledgment failure preserving service success, and idempotent repetition. Generate local `.eml` files using Nodemailer's Stream transport, which composes MIME without sending, to inspect multipart bodies and CID/photo attachment relationships. Use synthetic customer details in previews. [Nodemailer: Stream transport](https://nodemailer.com/transports/stream)

Preview narrow and desktop layouts, long addresses/details, no photos, and absent optional fields. A browser preview establishes layout evidence only. Gmail, Outlook and Apple Mail rendering, image-blocked behavior, inbox placement and actual authentication remain separate checks requiring received-message inspection; do not describe local tests as proof of those outcomes.

## Implemented and checked

Brand-font refinement: the owner selected the actual logo and branded headline artwork. `scripts/build-email-artwork.mjs` rasterizes the supplied vector logo and Brookvale font into PNGs. `pickup-email-artwork.generated.ts` carries those bytes in the server bundle. `withPickupArtwork` embeds the logo and audience-specific headline using Content-ID attachments, retaining all existing photo/consent attachments. HTML includes meaningful alt text; operational details remain live text and the plain-text alternative stays complete. This avoids remote fonts and image requests. Local browser previews substitute the same bytes into data URLs; delivered `.eml` files use CID references. MIME tests verify both images and continued crew-only private attachments.

Owner refinement: the crew email body now contains only a compact phone/email and SMS opt-in summary. The exact disclosure, timestamp, source and version are preserved in `contact-permission.txt`, attached to the crew email alongside any photos. This attachment is not included in the photo count or sent to the customer. The repeated scheduling reminder and customer phone paragraph were removed; those details already appear in the request summary. Tests cover retaining both consent and photo attachments in the delivered MIME.

The mailer now sends distinct crew and customer templates with inline styling, a text wordmark, full plain-text alternatives, a request reference, item/quantity table, readable notes and reply links. The crew message retains attachments and the consent audit record. The customer message has neither, uses its own Message-ID and service-mailbox Reply-To, and includes automatic-response suppression headers.

The existing API caches the combined delivery outcome. Customer-copy failure returns the accepted request reference with `confirmation: unconfirmed`, emits a warning containing only the reference, and shows save-your-reference guidance. There are no new environment variables, dependencies, remote image requests or tracking pixels. Email validation now also rejects address-list/group syntax so an acknowledgment has a single recipient.

Verification: 54 unit tests passed, including generated MIME, delivery ordering, partial failures, escaping and receipt parsing; lint, TypeScript, production build and isolated production HTTP checks passed. Browser previews covered the customer template at desktop and 390px viewport sizes, including a 4,000-character unbroken note with no horizontal overflow. Crew content was inspected separately. `npm run preview:email` regenerates synthetic HTML/text/EML examples. No live email was sent, and external inbox rendering/authentication are not verified by these local checks.
